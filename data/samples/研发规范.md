# 云雀科技研发规范

本规范约束代码提交、发布、故障处理等研发活动，适用于全部研发团队与外包研发人员。

## 一、分支与提交

主干分支为 main，禁止直接向 main 提交代码，所有改动必须通过 Pull Request 合并。

功能开发从 main 拉出 feature 分支，命名格式为 feature/需求编号-简述；修复分支为 hotfix/问题编号。

每个 PR 至少需要 1 名同组同事 Approve，核心模块（支付、鉴权、数据同步）需要 2 名 Approve，其中至少 1 名为模块 Owner。

单个 PR 改动行数建议不超过 400 行，超过的应拆分，便于评审与回滚。

## 二、代码评审

评审重点依次为：正确性、边界条件、错误处理、可读性、性能、安全性。

评审意见须在 1 个工作日内回复，作者修改后重新请求评审，禁止自行 Approve 自己的 PR。

涉及数据库变更的 PR，必须附带回滚脚本，并在评审中说明锁表风险与预估执行时长。

## 三、测试与质量门禁

单元测试覆盖率门槛为 60%，核心模块为 80%，未达门槛的 PR 无法合并。

所有 PR 必须通过 CI 流水线：静态检查、单元测试、依赖漏洞扫描，任一失败即阻断合并。

新增接口必须有集成测试，涉及资金与权限的逻辑必须有异常分支测试。

## 四、发布

常规发布窗口为每周二、周四 14:00 至 17:00，其他时间发布须提前申请并由研发总监审批。

发布采用灰度策略：先发布 5% 流量观察 30 分钟，无异常再扩至 50%，最后全量。

发布前须完成发布检查单，包括数据库变更确认、监控告警配置、回滚方案演练。

紧急修复（hotfix）可不受发布窗口限制，但须在发布后 24 小时内补齐发布记录与复盘。

## 五、故障复盘

P1 与 P2 故障必须在 3 个工作日内完成复盘，输出复盘文档并在研发周会上宣讲。

复盘遵循「对事不对人」原则，重点分析根本原因与流程缺陷，而非追究个人责任。

复盘必须产出可执行的改进项，每项明确责任人与完成时间，改进项完成率纳入团队季度考核。

同类故障在 6 个月内重复发生的，视为改进项未闭环，团队负责人须向 CTO 说明。
