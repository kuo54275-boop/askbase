# AskBase · 企业知识库问答系统

> 一个基于 RAG 的大模型应用：上传文档 → 混合检索 → 重排 → 带引用的流式回答。
>
> Python 3.11+ / FastAPI / DeepSeek / SQLite，**克隆下来 3 条命令就能跑**，没有 API Key 也能演示。

**[快速开始](#快速开始)** · **[架构](#架构)** · **[评测数据](#评测结果)** · **[设计取舍](#设计决策面试可以直接讲的部分)** · **[已知限制](#已知限制)**

```bash
git clone <this-repo> && cd <this-repo>
pip install -r requirements.txt
python scripts/seed.py && uvicorn app.main:app --reload
```

打开 <http://127.0.0.1:8000> 即可对话。**不配 API Key 也能跑**——会自动进入 Mock 模式。

## 为什么是「知识库问答」

企业里大模型最先落地的场景不是写诗，也不是让它当客服闲聊，而是**把公司自己沉淀的文档用起来**：
员工手册、产品文档、合同条款、运维 SOP。这些内容有三个特点——量大、更新快、答错了要担责。

所以这类系统的核心不是"调通 API"，而是三件事：

1. **检索准**：找得到相关原文（否则模型只能编）
2. **答得稳**：有依据、有出处、不知道就说不知道
3. **可度量**：改了一版切分策略，效果到底是变好还是变差，得用数字说话

这个项目把这三件事都做成了可验证的东西。

## 功能

| 能力 | 实现 |
|---|---|
| 文档解析 | PDF / DOCX / Markdown / TXT，含 DOCX 表格 |
| 切分 | 标题感知 + 中文句子边界 + 句子级滑动窗口 overlap |
| 检索 | BM25 关键词 + 字符 n-gram 哈希向量 + RRF 融合 |
| 精度控制 | 双路分数门控（相对断层 + 绝对相似度下限） |
| 生成 | DeepSeek 流式输出，SSE 推送；无 Key 自动降级 Mock |
| 引用溯源 | 每个结论标注 `[1]`，前端可展开原文核对 |
| 重排 | LLM 打分精排，Recall@1 94.34% → 100%，每 query 多约 460ms |
| 多轮对话 | 追问自动 query 改写（补全指代），模型不可用时退回启发式拼接 |
| 评测 | 53 条检索标注 + 20 条生成评测 + 20 条拒答样本 |
| 拒答 | 知识库没有的问题明确说"未提及"，擦边问题同样拒答（20/20） |
| 界面 | 单文件前端，零构建，支持上传/对话/评测 |

## 评测结果

`eval/qa_set.jsonl` 共 **53 条**人工标注问题，覆盖 7 篇文档（员工手册、财务制度、采购办法、客服 SLA、
研发规范、产品手册、IT 指南）。全部只用检索层，不调用大模型，所以**零成本、可进 CI**。

```
样本数：53
Recall@1: 94.34%      # 50/53 的第一条结果就是正确文档
Recall@3: 100.00%
Recall@5: 100.00%
MRR: 0.9717
平均检索延迟: 0.23 ms
```

> **怎么看待这组数字**：7 篇文档 / 41 个切片，规模仍然不大，但已经能测出差异——
> 新增的四篇制度文档刻意制造了**字面高度相似、语义完全不同**的难负例
> （"报销审批" vs "付款审批"、"IT 故障分级" vs "客服工单分级"、"发票作废" vs "合同用印"）。
> 这个集子的定位是**回归测试**：防止改切分参数或融合权重之后效果悄悄倒退。

三条没排在首位的样本，恰好是被新语料"带偏"的典型：

| 问题 | 被谁抢了第一 | 原因 |
|---|---|---|
| 请求太频繁会被怎么处理？ | 研发规范 | "处理"在两个文档里都高频出现 |
| 数据一般多久会自动清除？ | IT 服务指南 | 打印内容"24 小时后自动清除"，字面几乎一致 |
| 合同盖章要走什么申请流程？ | 财务制度 | 发票"加盖公章" vs 合同"用印申请" |

它们都在 Recall@3 内被召回——说明**"召回了但排不上来"是这类系统的常态失败模式**，
也正是重排（rerank）要解决的问题。

### 加重排之后

`python scripts/eval_rerank.py` 会对同一批问题跑两次（会真实调用 53 次模型）：

| 配置 | Recall@1 | Recall@3 | MRR | 延迟 |
|---|---|---|---|---|
| 粗排（BM25 + 向量 + RRF） | 94.34% | 100% | 0.9717 | **0.2 ms** |
| **+ LLM 重排** | **100.00%** | 100% | **1.0000** | 459 ms |

三条原本排第二的样本全部被救回第一。**但要诚实**：因为 Recall@3 本来就是 100%，
重排的理论上限就是把那 3 条提上来 —— 53 条样本上这是"3/3 全中"，不是"普遍提升 5.66%"。
真实业务里语料大了，粗排会漏到 top-5 之外，重排的上限和收益需要重新测。

代价也很明确：每个 query 多一次模型调用，**端到端延迟从约 1.4s 涨到约 2.5s**。
对交互式问答可以接受，对高并发场景要用本地 cross-encoder 替代。

## 生成质量评测

检索指标只能回答"资料找对没有"，回答不了"答案编没编"。这一层单独测。

`python scripts/eval_generation.py`，20 条正样本 + 20 条负样本：

| 指标 | 结果 | 怎么算 |
|---|---|---|
| 忠实度 | **2.00 / 2.00** | LLM 裁判打 0-2：每条结论是否都能在资料里找到依据 |
| 完全忠实率 | **100%** | grounded == 2 的占比 |
| 相关性 | **2.00 / 2.00** | 是否答到点上 |
| 引用准确率 | **100%**（20 个角标） | `[n]` 指向的资料是否真能支持那句话 |
| 拒答率 | **100%**（20/20） | 知识库里没有的问题，是否明确说"未提及" |
| 平均端到端延迟 | 1732 ms | 含改写、重排、生成 |

> 注：这张表是**单次裁判**的结果。改成"正序 + 倒序各判一次取平均"后，
> 忠实度是 **1.96 / 2.00**（见下面「复核」一节）——单次打分的整数满分偏乐观。

**负样本为什么要分两类**：前 15 条明显无关（股票代码、食堂几点开饭），
后 5 条是**擦边问题**——"员工每年有几天带薪病假""试用期几个月""离职提前多久提"。
这些问题在知识库里有相邻概念（病假证明、员工手册适用范围、离职归还设备），
最容易被模型"顺理成章"地编一个答案出来。两类全部拒答成功。

实际的拒答长这样（不是简单甩一句"不知道"）：

> 结论：资料中未提及员工每年带薪病假的天数。
> 依据：资料[1]仅说明病假需提供二级以上医院开具的病假证明，未规定带薪病假天数；
> 资料[2]仅说明手册适用范围和施行日期，也未涉及病假天数。[1][2]

### 复核：三重独立证据 + 双序平均

`python scripts/recheck_generation.py`（**50 条**样本），副裁判用**跨厂商的智谱 glm-4-flash**，
每个裁判对**正序 + 倒序各判一次取平均**：

| 检查 | 结果 | 说明 |
|---|---|---|
| 规则校验通过率 | **96.5%** | 不看模型，只验证「引用的资料是否支持那句话」；3 条误伤，见下 |
| chat 忠实度 | **1.97 / 2.00** | 双序平均后是小数——单次打分有 ±1 的位置噪声 |
| glm 忠实度 | **2.00 / 2.00** | 跨厂商裁判 |
| chat ↔ glm 一致率 | **100%**（50/50） | 四舍五入后完全一致 |
| 位置敏感样本 | **3/50（6%）**，平均差 1 分 | 倒序后分数变化的样本，被平均抵消 |
| 篡改检出率 | **100%**（7/7） | 人为把 `[1]` 改成 `[2]`，规则全部抓到 |

**稳定性验证**：25 条时 chat 1.96 / glm 2.00 / 一致率 100% / 位置敏感 8%；
扩到 50 条后是 1.97 / 2.00 / 100% / 6%。两次独立采样结论一致，**1.96~1.98 是稳的**。

**规则校验剩下的 3 条误伤分两类**（都人工核对过，答案是对的）：

| 类型 | 例子 | 为什么抓不住 |
|---|---|---|
| 同义改写 | 答案「可以报销，但需补充材料」 vs 原文「需提供丢失证明及记账联复印件」 | 字面重合度低 |
| 推断结论 | 答案「98% 属于该区间，故赔付 30%」 vs 原文「低于99.0%但不低于95.0%的赔付30%」 | `98` 来自问题而非资料，是推理不是引用 |

这两类是词法校验的天花板，不是实现缺陷。已经处理掉的两类才是我能修的：
**指代式总结句**（「依据：…上述…」）和**否定断言**（「资料中未提及 X」）——后者尤其重要，
模型在正确拒答时，规则却会因为"字面上找不到支持"而误判。

> 规则校验的定位是**下限，不是判官**：通过率低说明大概率有问题；
> 误伤集中在"同义改写"和"推断结论"，需要人看一眼再下结论。

副裁判支持**任意 OpenAI 兼容端点**（通义 / Kimi / 智谱 / 硅基流动 / OpenAI），
填 `JUDGE_API_KEY` + `JUDGE_BASE_URL` + `JUDGE_MODEL` 即可切换；
鉴权失败、端点写错时会打印可读原因（含服务端返回体）并自动回退到同厂商 R1，不会让评测脚本崩掉。

最后一行是关键：一个永远判"通过"的检查器是没有价值的。
所以专门做了**灵敏度测试**（`scripts/check_verifier_sensitivity.py`），
把答案里的引用编号集体错位一位，看规则能不能发现——5 条全部检出，
原文 2/2 通过、篡改后变成 0/2。这证明前面那个 100% 不是"什么都放过"。

> 规则校验在开发过程中还抓到一个真 bug：真实答案的角标写在句号后面（`…15天。[1]`），
> 按句号切分会把 `[1]` 切到下一条结论上，导致校验张冠李戴。已修复并把用例固化进测试。

### 这组数字的可信度边界

必须说清楚，否则就是自欺欺人：

1. **跨厂商复核只做了 25 条**。智谱 glm-4-flash 与 DeepSeek 在这 25 条上完全一致，
   但样本量还不足以断言"任何场景都一致"；裁判自身还有 ±1 的位置噪声。
2. **语料是干净的合成文档**。真实企业的 PDF 常有扫描件、版本冲突、过期条款，
   忠实度会明显下降。
3. **拒答判定基于关键词**（`is_refusal`）。可能把"未提及"误判成拒答，
   所以人工抽查了 3 条，确认模型是真的在逐条说明"资料里没有"，而不是碰巧命中关键词。
4. **规则校验是"下限"**。它抓的是数字错配和术语严重不匹配，
   抓不到"引用正确但推理错误"这种更隐蔽的问题。

## 消融实验

`python scripts/ablation.py` 在内存里重建索引跑对照组，不写库、不调模型，全量 <1 秒。

### 召回通路对比（同一标注集，53 条 / 41 切片）

| 配置 | Recall@1 | Recall@3 | MRR |
|---|---|---|---|
| BM25 only | **94.34%** | 100% | 0.9717 |
| 向量 only | 83.02% | 88.68% | 0.8553 |
| 混合（等权 1:1） | 92.45% | 100% | 0.9623 |
| 混合（等权，关闭门控） | 88.68% | 100% | 0.9403 |
| **混合（权重 0.6:0.2，默认）** | **94.34%** | **100%** | **0.9717** |

### 门控强度（BM25 侧）

| 门控阈值 | Recall@1 | 平均来源数 | 最多来源 |
|---|---|---|---|
| 关闭（0.0） | 90.57% | 5.00 | 5 |
| 0.50 | 94.34% | 2.21 | 5 |
| **0.65（默认）** | **94.34%** | **1.94** | 5 |
| 0.80 | 94.34% | 1.70 | 5 |

门控不只是省 token，它直接提升精度：不裁剪时每条查询都塞满 5 条来源，
Recall@1 只有 90.57%；裁剪后平均只剩 1.94 条，Recall@1 反而升到 94.34%。

选 0.65 而不是 0.80：两者召回相同，但 0.80 更激进，换一批语料更容易误伤"次要但有用"的切片
（多要素问题需要多条来源）。这是一个**保守优先**的选择，不是最优点。

### 最重要的一个反直觉结论

**朴素等权 RRF 比纯 BM25 还差 1.9 个百分点（92.45% vs 94.34%）。**

原因：RRF 只看名次，而两路召回的质量并不对等。哈希向量排第 1 的切片，
可能只是"共享了几个汉字"，它在 BM25 里排第 10；但等权相加后
`1/61 + 1/70` 竟然超过了 BM25 真正的第 1 名 `1/61 + 1/75` —— **噪声被投票放大了**。

修复方式是给两路不同权重（向量只占 0.2），指标回到 94.34%，与纯 BM25 持平。

> 必须诚实的一点：0.6:0.2 和等权之间只差 **1 个样本**，在 53 条样本上不具统计显著性。
> 有说服力的表述是"等权融合没有带来增益，且存在被弱通路拖累的风险"，
> 而不是"我调出了最优权重"。换成语义能力更强的 bge 向量后，这组权重必须重新标定。

其余结论：

1. **向量单独用只有 83%**，且 Recall@3 只有 88.68% —— 低于 BM25 的 100%。
   这说明"上了向量"不等于"效果更好"，必须给对照组。
2. **门控不是可有可无的调优**：关掉后等权融合从 92.45% 掉到 88.68%。
   噪声切片挤进前 k，把正确文档顶下去——"少召回"和"召回了但排不上来"是两回事。
3. **切分参数（300/400/600 × overlap 0/60/120）和 RRF 的 k（10/60/100）依然无差异**。
   41 个切片的语料仍然装不下这个维度的区分度，要等语料上到几百篇。

> 诚实的边界：53 条样本能做回归和通路对比，但不足以证明某个参数全局最优。

## 设计决策（面试可以直接讲的部分）

### 1. 为什么用 RRF 融合，而不是把分数加权相加？

BM25 分数是无界正值（本例中 19.8 / 8.6），余弦相似度是 `[-1, 1]`，两者量纲不同。
加权相加必须先归一化，而归一化方式（min-max / z-score）会引入超参，换一批数据就得重调。

RRF 只使用**名次**：`score = Σ w / (k + rank)`，对分数尺度完全免疫，k=60 是论文里的经验值。

注意这里的 `w`：**两路的权重不能简单取 1:1**。当一路召回明显弱于另一路时，
等权融合会让弱通路的噪声拿到同样的票数，反而拖累整体（消融里等权 92.45% < 纯 BM25 94.34%）。
权重要么按召回质量标定，要么直接给弱通路降到 0.2 这种量级 —— 详见「消融实验」。

### 2. 为什么还要加"分数门控"？

RRF 的问题恰恰是它不看分数高低：一个余弦 0.02 的垃圾切片和一个 0.14 的高相关切片，
只要名次相邻，融合分几乎一样（0.0328 vs 0.0315）。这些噪声会一起进 prompt，稀释上下文。

所以在融合**之前**各裁各的：

- 向量侧：低于 `top × 0.4` 或低于该向量表示的经验下限（哈希向量为 0.05）→ 丢弃
- BM25 侧：低于 `top × 0.5` → 丢弃（BM25 分数通常有明显断层）

两路独立裁剪的好处：**某一路误裁了正确切片，另一路还能把它召回来**。这正是混合检索比单路更稳的原因。

效果（53 条评测集实测）：**平均来源数 5.00 → 1.94 条，Recall@1 反而从 90.57% 升到 94.34%**。
噪声少了，精度还高了——因为被裁掉的切片本来就在把正确文档往下挤。

### 3. 为什么 embedding 用哈希向量，不用 bge？

- 中文 embedding 模型动辄几百 MB，还要 torch。面试现场换台电脑就跑不起来，风险太高。
- 哈希向量（字符 2-gram / 3-gram + signed hashing trick + L2 归一化）完全确定性、零下载、零网络。
- 关键是**接口抽象**：`EmbeddingProvider` 协议只有 `embed()` 和 `min_similarity`，换 bge-m3 只改工厂函数一行，
  检索层、融合层、评测脚本全部不动。

这是一个明确的工程取舍：先用可替换的基线把链路跑通，效果不够再换重武器。

### 4. 为什么不落库向量？

SQLite 只存原始文本。启动时从文本重算向量——因为哈希向量是确定性的，重算成本极低（41 个切片 <1ms）。

好处：**永远不会出现"库里的向量和当前代码/模型不一致"这种脏数据**。这是 RAG 项目最常见的线上事故之一。

### 5. 为什么用 SSE 而不是 WebSocket？

问答是"客户端发一次、服务端推多次"的单向流。SSE 基于普通 HTTP，天然兼容反向代理、
断线重连、HTTP/2，实现和运维成本都更低。记得设 `X-Accel-Buffering: no`，否则 Nginx 会把流攒成一次性输出。

### 6. 为什么要做 Mock 降级？

没有 API Key 时自动改用"从检索结果抽取句子"的 Mock 客户端，接口完全一致。

价值：克隆下来立刻能演示、单测不消耗 token、CI 不依赖外部服务。
这不是玩具——它保证了**任何人拿到这个仓库都能在 30 秒内看到完整效果**。

### 7. 多轮为什么先做「query 改写」而不是直接拼历史？

多轮检索最容易踩的坑：用户问「那没休完怎么办？」，直接把这句话丢给检索，召回率接近 0——
因为"没休完"和原文里的"结转"没有任何字面重叠。

所以有历史时先用一次短调用把追问改写成**可独立检索的完整问题**
（`那没休完怎么办？` → `年假没休完可以结转到明年吗？`），再去检索。

两个工程细节：

- **没有历史就不调用**，省一次请求和几百毫秒；
- **改写失败一律退回启发式拼接**（上一轮问题 + 当前追问），保证多轮能力不会因为模型抖动而整体不可用。
  Mock 模式走的就是这条兜底路径，所以离线也能测多轮。

### 8. 切分为什么按"句子"而不是按"字符数"？

按字符硬切会把一句话从中间劈开，检索命中半个句子，生成时上下文不完整。
这里先按标题切 section，再按中文句末标点切句，最后做句子级滑动窗口，overlap 用尾部完整句子构造。

代价是切片长度不完全均匀（允许超 30%），换来的是语义完整性。

### 9. 重排为什么用 LLM，而不是 cross-encoder？

标准答案是 bge-reranker 这类 cross-encoder：快、准、不花钱。但在这里它有三个现实成本：

1. **体积**：torch 运行时装完约 2GB，模型再 1.1GB。这个项目的卖点是"克隆下来就能跑"。
2. **首启时间**：CPU 上冷启动加载模型要十几秒，演示时很难看。
3. **平台风险**：`torch` 在 Windows + 新 Python 版本上经常没有预编译 wheel，装不上就全盘卡住。

用 LLM 打分排序（listwise）的优势是**零新增依赖**，代价是每 query 多约 460ms 和一次 API 调用。

关键在**抽象**：`Reranker` 协议只有 `rerank(question, sources, top_k)` 一个方法，
换成 cross-encoder 只需要新增一个实现类，`rag.py` 一行不用改。
这也是我选它的真实原因——先用零依赖方案把"重排有效"这件事验证出来（+5.66pp），
再决定值不值得为它引入 2GB 的运行时依赖。

> 另外，重排失败必须静默降级回原顺序。重排是"锦上添花"，
> 不能因为它超时或输出格式错误就让整个问答挂掉——`tests/test_rerank.py` 覆盖了这两种情况。

## 已知限制

诚实列出，面试被问到时不会翻车：

1. **多轮能力是"改写 + 最近 4 轮上下文"**，没有做完整的对话状态管理，超长对话会丢早期信息。
2. **重排用的是 LLM 而非 cross-encoder**：准但慢（+460ms/次），高并发场景需要换本地模型。
3. **评测集仍然偏小**：53 条、7 篇文档，能做回归和通路对比，但不足以调参；切分维度至今没有区分度。
4. **无 OCR**：扫描版 PDF 解析不出文本。
5. **无权限体系**：所有文档对所有人可见，生产环境需要按部门/文档库隔离。
6. **单机 SQLite**：并发写入能力有限，多实例部署要换 Postgres。
7. **生成评测的裁判和生成是同一个模型**：存在自我偏好偏差，分数可能偏乐观；没有做人工复核。
